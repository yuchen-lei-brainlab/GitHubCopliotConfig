# Shared Nightly Guidance

- Before creating a changelist, discovering files, or running checks, identify the Perforce workspace containing the requested package or the pending changelist. For a changelist, verify its client and use that client's root; for a package, verify that it is mapped in the selected client. Do not update a different workspace.
- In a new Developer PowerShell window with the user profile loaded, select that workspace and its root, confirm `p4 login -s`, then run `pt updateclient -c <client-workspace-name>` from the workspace root. Ensure the profile's `$CLIENT_ROOT` and Perforce client match the selected workspace. Do not use `-d` (it deletes the sandbox) or `-y` (it automatically answers yes); if a prompt cannot be handled safely, stop and report it. Check the command's exit status and the `pt-log.txt` produced by this run for errors and warnings; resolve any update problems before continuing. If the workspace, login, update, or its result cannot be verified, stop and report the blocker. Do not force-sync, revert, or overwrite opened files to make the update succeed.
- This workspace update also precedes pre-commit **check** mode: it updates the workspace but must not edit files or change the changelist. Run long checks in a new Developer PowerShell window with the user profile loaded.
- Whenever creating or updating a Perforce changelist description, check whether the changelist contains test files. If it does, include a separate `REVIEW: test changes` line; preserve existing description text and keep any required `CHANGED:` prefix at the start. Do not add a duplicate `REVIEW:` line if one is already present.
- Clang-tidy needs Windows Python (`C:\Program Files\Python313\python.exe`); IWYU needs the profile's default Cygwin Python.
- Preserve justified existing analyzer suppressions and the code they protect; do not remove them or change an API solely to appease another analyzer. For example, retain a reference-returning thread-local generator and its `//lint !e1929` annotation rather than returning a pointer, and keep a macro's `//lint !e750` annotation when it is used by third-party headers.
- Preserve explicit lambda captures when they are intentional; replacing `[this, &event, count]` with `[&]` can introduce lint findings. Keep established `CHKSTD_OK` test-header comments unchanged unless a finding actually requires changing them.
- If modified tests belong to a separate test package, run its lint independently in a new Developer PowerShell window; linting the parent package may not include test sources. Review numbered findings and exit status, and report any failed tool or build as a blocker.
- Doxygen can print progress through stderr as `NativeCommandError`; distinguish this from actual warnings or errors. IWYU include changes must be followed by a lint or normal build to confirm they compile.
- Doxygen warnings usually mean missing or incorrect `@param`, `@return` or `@brief` comments.
